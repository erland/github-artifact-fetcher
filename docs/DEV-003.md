# DEV-003 – PostgreSQL and automatic Flyway startup
The runtime uses its own PostgreSQL database `github_artifact_fetcher`, and least-privileged user `github_artifact_fetcher_app`. The database and role are provisioned once by the operator, not by application migrations.
Run `docker compose -f compose.yml up -d --build`: an ephemeral Flyway service migrates the database before the application starts. Every restart of the Compose project reevaluates Flyway; existing migrations remain idempotently recorded in `flyway_schema_history`. The runtime is not started if migrations fail. Readiness checks database connectivity and the required migrated table.
Separate credentials: `FLYWAY_JDBC_URL`, `DATABASE_MIGRATION_USER`, `DATABASE_MIGRATION_PASSWORD` for migration, and `DATABASE_URL` for runtime. Flyway migration role must own the schema and tables; runtime role has DML only, with grants declared by migrations.
The Docker image alone does not run migrations; use Compose or an equivalent Coolify pre-start migration job that enforces the success dependency. This design deliberately avoids Java in the Node.js runtime.
Security: Flyway clean disabled by default; do not use a database superuser for normal runtime. Tokens are encrypted by a later development step. No service has been deployed.
