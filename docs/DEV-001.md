# DEV-001 – MCP file handoff PoC

## Scope and limits
A dependency-free Node 22 MCP Streamable HTTP proof of concept with `initialize`, `tools/list`, `tools/call`, a 5-minute signed HTTPS-compatible file URL, an MCP `resource_link`, size and SHA-256. Demo fixtures only; no GitHub access, no OAuth, no database, no publication to Internet and **no ChatGPT `file_id` generated**.

## Local verification
Run `npm run test:poc`. Then `POC_SIGNING_SECRET=<at-least-24-characters> npm run start:poc`. The fixture is retrieved by MCP `tools/call` and the returned URL can be fetched as bytes; tests check matching SHA-256 for EPUB/PDF/ZIP, rejected tampered signature, bad fixture, and the tool handshake.

## Critical acceptance gate: NOT YET PASSED
Actual ChatGPT plugin must connect to deployed HTTPS endpoint, invoke `poc_fetch_fixture`, and prove that the binary can be read in ChatGPT as a file, not just displayed as a link. Test both `resource_link` rendering and file handoff. A `structuredContent.file_uri.file_id` must *not* be fabricated: it requires a genuine ChatGPT/connector file handoff provider. If the runtime cannot provide it, record the limitation and revise the integration design. No production deployment should proceed assuming this works.

## Security / lifecycle
This PoC is **not for public deployment**: MCP endpoint has no OAuth; temporary links are signed and short lived but URLs are bearer capabilities. No arbitrary URL fetching or remote upload. To deploy for acceptance, restrict access and implement the OAuth/security boundary or temporarily isolate the service; later steps handle production hardening.

## Decision 2026-10-16: defer deployment-dependent acceptance
The user explicitly requested no deployment at this stage. DEV-001 is considered **locally complete, with external acceptance deferred**. This is not a PASS for ChatGPT-native outbound file attachments and does not waive the release gate. The next step is DEV-002. Complete the deferred end-to-end gate in DEV-010 or earlier when a protected deployment is available.

### Existing evidence from `erland/agent-workspace` (main, inspected 2026-10-16)
- `src/artifact/artifact-download.ts`: HMAC-SHA256 signed, expiring artifact URLs bound to artifact/user; reusable security pattern, not a ChatGPT-file handoff implementation.
- `src/mcp/artifact-resource.ts`: MCP resource URI `agent-workspace://artifacts/{artifactId}`; a resource URI alone is not an OpenAI `file_id`.
- `src/mcp/tool-service.ts` and README: OpenAI file parameters (`_meta["openai/fileParams"]`) support **inbound** ChatGPT attachment -> MCP service; `workspace_upload_zip_from_url` supports inbound remote URL transfers.
- `docs/artifact-handoff.md`: `artifact_download_link` -> signed HTTPS URL -> PWA Preview is a tested/defined **service-to-service** handoff, not evidence of native attachment delivery to ChatGPT.
- Earlier conversation tested the GitHub connector's `download_workflow_artifact`, which returned a provider-managed `file_uri.file_id` and a ZIP file. This demonstrates a compatible connector transport exists, but not that generic `resource_link` from a custom server auto-produces a managed `file_id`.

### Design requirements carried forward
1. Preserve a transport abstraction: temporary artifact stream + metadata/digest + signed URL, plus an optional connector-managed handoff adapter if the host supports it.
2. Never fabricate or promise managed `file_id` from a plain MCP URL/resource link.
3. Release acceptance must invoke the real GitHub Artifact Fetcher plugin in ChatGPT, fetch EPUB/PDF/ZIP from GitHub, and verify that their bytes can be analyzed as files within the ChatGPT conversation.
4. If the host only renders a URL, document this as a failure of native file handoff, not success; explore supported connector file export/API integration.
5. No new service deployed to conduct DEV-001 in this run.
